## Core Scientific Question

This analysis asks whether individual differences in social preferences are best understood as:

> **A. one shared utility architecture with different participant-level parameters**,
> or
> **B. heterogeneous utility architectures, where different participants are better described by different functional forms.**

The existing IC analysis identifies the best utility function at the population level. This new analysis asks whether that population winner is a true shared coordinate system or a compromise over different participant-specific architectures.

Do not treat this as just a visualization task. The goal is to quantify how much predictive and geometric evidence there is for **functional-form heterogeneity**.

The code should reuse the existing IC, utility, AMPD, nesting, and fit-output machinery. Follow the repo's style conventions: long descriptive names, keyword arguments, project import-flow discipline, and docstrings with bullet-style arguments.

**Most important conceptual warning:**
> Participant architecture is not a fitted parameter vector. It is a **distribution over utility functional forms**, derived from per-participant model evidence.

**Second most important warning:**
> Cross-validated `H_form` tests whether individualized forms help; the compression curve tests **how many forms are needed**. Without Stage 9, the analysis will not finish the thing we set out to do.

Output: `processed/participant_model_role_fits.csv`

### Combined-role participant fit table
Output: `processed/participant_model_combined_fits.csv`

Each row = player_uuid × utility_idx. Key columns:
- `chooser_loss_nll`, `predictor_loss_nll`, `combined_loss_nll`

## Stage 7 — Participant Cloud Distances

### Purpose
Turn each participant's model-support cloud into participant-level distances and embeddings.

Each participant = `{utility model m → BIC weight w_i,m}`

### Two ways to place participants in model space

**1. Visualization centroid**
Place participant i at the BIC-weighted centroid of model MDS coordinates:
`z_i = sum_m w_i,m * z_m`
Output: `processed/participant_model_space_centroids.csv`

**2. Participant cloud distances (more principled)**

Expected cross-cloud distance: `cross_ij = w_i^T D_model w_j`
(useful as descriptive measure; gives positive self-distance when cloud is diffuse)

Energy-style distance (use for MDS/clustering):
```
within_i = w_i^T D_model w_i
energy_distance_ij = sqrt(max(0, 2 * cross_ij - within_i - within_j))
```
This ensures `energy_distance(i, i) = 0`.

Outputs:
- `processed/participant_cloud_distance_matrix__metric=ampd_energy.csv`
- `processed/participant_cross_cloud_distance_matrix__metric=ampd.csv`

### Participant MDS
Embed using energy-style cloud distance matrix.
Output: `processed/participant_architecture_embedding.csv`

Visualizations: color by top model, cluster, feature-support probabilities, fitted parameters.

### Feature-support summaries
For each participant and each Boolean utility setting:
`P_i(setting=True) = sum_m w_i,m * 1(setting_m=True)`
Output: `processed/participant_feature_support.csv`

## Stage 8 — Cross-Validated H_form

### Purpose
Test whether participant-specific utility architectures improve held-out prediction beyond a common shared architecture.

### H_form definition
```
H_form = (NLL_common - NLL_individual) / (NLL_chance - NLL_individual)
```
- H_form = 0: individual forms add nothing
- H_form > 0: participant-specific forms improve prediction
- H_form < 0: participant-specific forms predict worse than common
- H_form ≈ 1: common architecture performs much worse

`NLL_chance = n_test * log(2)` for binary choices.

### Cross-validation design
- Role-stratified folds within participant
- Use train loss to select individual model; evaluate on test loss
- Label full-data fits as `in_sample_H_form`

### Outputs
- `processed/h_form_cross_validated_results.csv` (fold_id, player_uuid, model indices, NLLs, h_form, n_test)
- `processed/h_form_cross_validated_summary.csv`

## Stage 9 — Functional-Architecture Compression Curve

### Purpose
Estimate how many distinct utility architectures are needed to describe participant differences.

Use actual utility functions as codebook **medoids** (not abstract centroids).

### Loss under K-architecture codebook
```
L_i(S_K) = min_{m in S_K} L_i(m)
NLL(K) = sum_i L_i(S_K)
```

### Normalized compression curve
```
A(K) = (NLL(1) - NLL(K)) / (NLL(1) - NLL(N))
```
- A(1) = 0: one common architecture
- A(N) = 1: every participant can have their own architecture
- A(3) = 0.85 means three architectures capture 85% of the benefit of full individualization

### Codebook selection: greedy forward
```python
select_architecture_codebook_greedy(
    participant_model_loss_df,
    max_k,
    selection_loss_column="train_loss_nll",
)
```
Select codebooks using train loss; evaluate on test loss.

### Preferred K
Report multiple criteria: elbow detection, one-SE rule, marginal-gain threshold (<1–2%), bootstrap stability, interpretability.

### Outputs
- `processed/architecture_compression_curve.csv` (K, train_nll, test_nll, A_K_train, A_K_test, marginal_gain, codebook_model_idxs)
- `processed/architecture_codebook_assignments.csv` (fold_id, K, player_uuid, assigned_model_idx, test_nll)
