# Model Recovery Simulation
## Calibrating the utility-function search instrument in *Inferring Hidden Motives*

> **Purpose**
>
> This file specifies a new simulation and model-space analysis for validating the paper’s **utility-function Information Criterion (IC) search**.
>
> The paper already validates the **optimizer** and the **belief-updating machinery** with simulation and human-bot data. What is still missing is a clean answer to a different question:
>
> **If data are generated by a known utility function, can the IC pipeline recover that function — or at least recover the correct behavioral equivalence class?**

---

## Why this matters

The paper’s core empirical architecture depends on four interlocking elements:

1. **Randomized binary dictator-game payoffs** over a broad payoff space.
2. **Explicit prediction elicitation** to isolate beliefs from choosers’ own preferences and strategic reasoning.
3. **A Utility Bayesian Model (UBM)** for social-preference belief updating.
4. **A full-model utility-function search** to determine which utility function should sit inside the model’s likelihood term.

That fourth step is load-bearing. The paper compares **the full valid utility-function universe**, defined by **14 Boolean utility settings**, over a payoff space that can span the full binary-dictator grid of **\(5^4 = 625\)** payoff structures in the human-human task. The IC analysis also uses a nesting network, parent-child verification, and parent-fair regularization to make the search scientifically defensible. The best model in the current manuscript is a **7-parameter** utility form, and the surrounding analyses include pairwise setting contrasts, robustness iterations, and nested-model logic.

So this simulation is not cosmetic. It calibrates one of the paper’s main scientific instruments.

---

# The three distinct validation questions

The current project now has **three** separable calibration targets:

## 1. Parameter recovery
**Question:** given the correct utility form, can the optimizer recover known parameters?

This is already partly done in the manuscript. The current simulation shows, among other things, that the optimizer recovers a known predictor altruism parameter with a strong correlation and that posteriors converge toward the chooser’s true parameter over repeated observations.

## 2. Utility-form recovery
**Question:** given data generated by a known utility function, can the IC pipeline recover the generating function, a simpler nested equivalent, or a behaviorally equivalent alternative?

This is the **new analysis** described here.

## 3. Data adequacy / information sufficiency
**Question:** did the actual study collect enough participants and enough games for recovery to stabilize?

This is the **“knee of the curve”** analysis.

---

# Core philosophy: exact top-1 recovery is too strict

A dumb scoring rule would be:

> *“If the true generating model is ranked #1, the IC analysis works. Otherwise it fails.”*

That rule is too harsh for this problem.

Why?

## Finite-data and stochasticity reasons
- payoff structures are sampled;
- agent parameters vary;
- SoftMax temperature introduces stochastic choice;
- finite datasets make some models hard to separate.

## Structural reasons
- many models are **nested**;
- a parent can collapse into a child at special parameter values;
- a child can be the *correct BIC winner* if the parent’s extra freedom is behaviorally inactive.

## Behavioral-equivalence reasons
Two distinct symbolic formulas can make nearly identical predictions over the observed payoff space. If the recovered model is behaviorally indistinguishable from the true model, treating that as “failure” would be silly.

So the goal is **graded calibration**, not binary purity.

---

# Recommended high-level strategy

Use a **layered validation framework**:

1. **Exact recovery**
2. **Top-\(k\) / BIC-set recovery**
3. **Nested-equivalent recovery**
4. **Behavioral-equivalent recovery**
5. **Feature recovery**
6. **Data-sufficiency curves**
7. **Self-consistency / noise ceiling**

---

# The main simulation to build
## Utility-function recovery simulation

This is the core loop:

1. Choose a **generating utility function** \(m^\*\).
2. Generate synthetic agents with parameters sampled from some regime.
3. Generate synthetic choices from those agents over repeated bDG payoff structures.
4. Run the **existing IC analysis pipeline** over the candidate utility functions.
5. Record where the true function ranked, how close the winner was behaviorally, which Boolean settings were recovered, and how performance changes with more data / lower noise.

---

## Main recommended version: heterogeneous-agents recovery

This is the version most worth treating as the **main result**.

### Setup
- All simulated agents share the **same generating utility form** \(m^\*\).
- Each agent receives its **own parameter vector**.
- Candidate models are fit **agent-by-agent**.
- Losses are then aggregated across agents to produce model rankings.

This best matches the scientific idea that a population can share a utility *family* while differing in individual parameter values.

### Why this version matters
It tests whether the IC machinery can recover **functional structure under heterogeneity**, not just in a toy homogeneous world.

---

## Optional supporting versions

### A\* — homogeneous sanity check
- Same generating form.
- Same parameter vector for all agents.
- Repeat across several deliberately chosen parameter vectors.

Use this to ask:

> **When the recovery problem is clean, does the IC analysis behave sensibly?**

This is useful as a sanity check, but not sufficient on its own.

### C — population-level stress test
- Same generating form.
- Different parameters per agent.
- Fit one population-level parameter vector per candidate model.

This is interesting because it stress-tests the approximation used in the paper’s current population-level IC analysis. It is also computationally cheaper than a full individual-level fit. But it should be treated as a **stress test**, not the clean main recovery analysis.

---

# Computational cost-cutting decisions

The full factorial grid described in this document (3 regimes × 3 temperatures × multiple dataset
sizes × multiple generating models) is computationally prohibitive. The IC pipeline calls
global-then-local optimization per (agent × candidate model) pair: at 73 agents × 480 models
= 35,040 fits per simulation run, each run takes roughly 1–2 hours even with full parallelization.
The decisions below scope the implementation to what is scientifically necessary.

## Role: chooser only

**Decision:** synthetic agents are generated as choosers only. Predictor role is not simulated.

**Reason:** the UBM predictor role runs the full sequential Bayesian belief-updating pipeline
(`agent()`) over all games, which is the most expensive operation in the codebase. Generating
predictors would double or triple computation time per agent with no benefit for the recovery
question. The IC analysis is primarily about recovering the *chooser's* utility function from
their allocation choices. Chooser NLL is the dominant signal in the combined loss anyway.

## Temperature: fixed at 0.5 (low noise)

**Decision:** the SoftMax temperature is fixed at τ = 0.5 for the primary simulation.
Temperature remains a function argument so it can be varied if needed, but the default
run uses only τ = 0.5.

**Reason:** a lower temperature makes choices more deterministic, which maximizes the
signal-to-noise ratio for recovery. The primary question — *can the IC pipeline identify
the correct utility form?* — is best answered in the cleanest setting first. τ = 0.5 is
also within the range of the fitted temperature values from the actual experiment, so it
is not an unrealistically clean setting.

## Parameter regime: realistic only as the primary

**Decision:** the primary simulation uses the realistic parameter regime (parameters drawn
from the empirical distribution of fitted participant values). The diagnostic and near-anchor
regimes described below remain in the plan as secondary checks but are not run by default.

**Reason:** the most scientifically important result is whether the IC pipeline works under
conditions that resemble the actual experiment. The diagnostic regime is useful only as a
sanity check. The near-anchor regime is interesting but the paper already addresses this
through its nesting network and parent-fair regularization.

## Generating models: IC winner (model 443) first

**Decision:** model 443 (the population IC winner, a 7-parameter form) is the primary
generating model. A small number of structurally distinct alternatives are run secondarily
to check that the IC pipeline can distinguish different utility families.

**Reason:** the most important question for the paper is whether the IC pipeline can
recover its own winning model under realistic data conditions. If it can, the analysis
is validated. If it cannot, that is a problem worth knowing about.

## Dataset size: vary n_games using nested subsets

**Decision:** n_games is varied from approximately {20, 40, 60, 90, 120, 180, 240} while
n_agents is fixed at 73 (matching the actual study). This produces the knee-of-the-curve
analysis that addresses whether the actual study collected enough data.

Synthetic data is generated *once* per generating model (240 games × 73 agents). For each
n_games value, only the first n_games games per agent are used. This nested-subset design
means all n_games conditions share the same agents; differences in recovery are attributable
purely to data quantity, not to agent-sampling luck. No separate replications are needed.

**Reason:** the user specifically identified "addressing whether we collected enough data"
as a core objective. Varying n_agents is secondary; the actual study is fixed at 73
participants and the more actionable question is whether 120 games was sufficient.

## Candidate model filtering: max-diversity subset, not BIC-ranked

**Decision:** when running the recovery search over fewer than all 480 candidate models for
speed, filter by *maximum behavioral or structural diversity* — not by BIC ranking from the
real data.

**Reason:** filtering by real-data BIC would bias the candidate set toward models that happen
to fit the real participants well, which has no principled relationship to which models are
most challenging to distinguish from the generating model. A max-diversity filter gives a
harder and more principled test: if the IC pipeline can recover the true model from a maximally
spread-out candidate set, it demonstrates genuine discriminability. Filtering by BIC could
accidentally exclude the true model or inflate recovery rates by removing structurally similar
alternatives.

**Implementation:** use `select_utility_settings_subset` (in `utilities.py`) with:
- `selection_mode='ampd'` and `distance_matrix_path` pointing to the precomputed AMPD matrix
  (preferred — behaviorally diverse candidates), or
- `selection_mode='hamming'` (cheaper — structurally diverse by Boolean settings)

Always include the generating model in the candidate set via `include_model_idxs`. The
`compute_hamming_distance_matrix` function in `utilities.py` handles the Hamming case.
Both modes implement max-min greedy selection: seeds with the IC winner, then repeatedly
adds the candidate with the largest minimum distance to any already-selected model.

## Parameter sampling: model-specific fitted values, not pooled

**Decision:** when generating synthetic data under generating model M*, sample parameters
from the empirical distribution of fitted values for model M* specifically (i.e., from the
IC JSON's `ic_results[M*]` participant fits), not from the pooled distribution across all
480 models.

**Reason:** pooled sampling draws from all models — including models without altruism, where
Vᵢⱼ is structurally zero or meaningless. This would corrupt the parameter distribution for
a generating model that actively uses altruism. Model-specific sampling ensures the synthetic
agents operate in the realistic parameter region for that specific utility form.

**On circularity:** this design is *not* circular. The IC pipeline sees only (payoffs, choices)
and has no access to the true parameters or generating model identity. It earns the recovery
result by fitting all candidate models from scratch and ranking by BIC. Using model M*'s
fitted participant parameters as the generating distribution is appropriate — it puts synthetic
data in the realistic operating range for that utility form, which is exactly the condition the
paper's main results apply to.

---

# Parameter sampling regimes

The realistic regime is the primary. The diagnostic and near-anchor regimes are secondary
sanity checks. Do **not** use only one parameter regime in the full analysis, but the
realistic regime is the required minimum.

Use at least three:

## 1. Diagnostic regime
Deliberately avoid degeneracies and anchor values.

Examples:
- altruism clearly nonzero if included;
- exponent clearly not equal to 1 if included;
- envy and guilt clearly different if split;
- self-interest clearly not fixed to 1 if that setting is free.

This asks:

> **Can the IC analysis recover the true form when the form is genuinely identifiable?**

If recovery fails badly here, that is a red flag.

## 2. Realistic regime
Draw parameters from plausible human-like distributions.

This can be based on empirical estimates from the paper, but should be labeled as a **realistic regime**, not as “proof.” Using empirically motivated parameters is fine here because the purpose is realism, not circular confirmation.

## 3. Near-anchor regime
Generate parents with parameters near child-anchor values.

Examples:
- altruism term near zero;
- self-interest near 1;
- exponent near 1;
- split envy/guilt terms nearly equal.

This asks:

> **Does the IC analysis appropriately prefer simpler children when the parent’s extra degree of freedom is behaviorally inactive?**

This is especially important because the paper already uses a formal nesting network and parent-fair regularization.

# Noise and information regimes

Recovery should vary predictably with **choice stochasticity** and **dataset size**.

## Choice temperature

**Default: τ = 0.5 (fixed).** See the cost-cutting decisions section for rationale.
Temperature remains a function argument and can be varied for secondary analyses,
but the primary simulation does not sweep over temperature values.

Low temperature makes models easier to distinguish. High temperature makes everything
look more random. If temperature is varied in a secondary run, suggested values are:

```text
tau in {0.5, 1.5}
```

Two values (low noise and realistic noise) are sufficient to bound the range.

## Number of games per agent

Vary the number of observed games to produce the data-adequacy curve. Suggested grid:

```text
n_games in {20, 40, 60, 90, 120, 180, 240}
```

n_games = 120 is the actual study design. The curve should flatten near 120 if the study
collected sufficient data.

If `n_games >= 625`, use the **full payoff grid** and skip payoff randomization.

## Number of agents

**Fixed at 73 (matching the actual study)** for the primary data-adequacy curve.
n_agents can be varied in a secondary analysis, but varying n_games is more directly
relevant to the paper’s question of whether the actual study was adequately powered.

Together, the `n_games` grid gives the **knee-of-the-curve** analysis:
- below the knee: recovery unstable / noisy;
- near the knee: big gains from more data;
- above the knee: diminishing returns.

# The core distance/loss idea
## Average Model Policy Distance (AMPD)

**Average Model Policy Distance (AMPD)** is the umbrella term for behavioral distance between utility-function policies. It is not a symbolic distance between equations. It asks how differently two utility forms behave when they are evaluated over the same payoff structures and comparable parameter draws.

For a utility model `m`, payoff structure `x`, and parameter vector `theta`, the static choice policy is:

$$
p_m(A \mid x,\theta)
$$

For two models, `m_a` and `m_b`, AMPD averages a distance between their induced choice probabilities:

$$
\text{AMPD}(m_a,m_b)
=
\mathbb{E}_{\theta,x}
\left[
    d\left(
        p_{m_a}(A \mid x,\theta),
        p_{m_b}(A \mid x,\theta)
    \right)
\right]
$$

where:

- `x` is a binary dictator-game payoff structure;
- `theta` is a shared reference parameter draw;
- `d(...)` is a policy-distance metric, usually normalized Jensen-Shannon distance.

AMPD is needed because IC ranks alone do not reveal the geometry of model space. A rank table can say which model won. AMPD can show whether the winner is surrounded by nearly identical neighbors, whether several distinct model families are competitive, and whether a model selected in a recovery simulation is behaviorally close to the true generating model even when it is not symbolically identical.

---

## AMPD is static utility-policy distance, not Bayesian-updating distance

Primary AMPD must compare utility functions as static choice policies:

```text
utility settings + parameters + payoff structure → p(choose A)
```

Do **not** include dynamic UBM belief updating in the primary AMPD calculation. Dynamic updating would make the distance depend on priors, observation histories, particle-filter settings, learning trajectories, and the full UBM. That may be useful later, but it would no longer be a clean distance between utility functions.

A dynamic-updating version can be added later as a clearly labeled secondary metric. The primary AMPD matrix used for MDS, clustering, max-min subset selection, top-model coherence, and participant model-cloud geometry should use static `utility(...)` → `softmax_(...)` choice probabilities.

---

# The critical AMPD rule: shared parameter draws

## Primary AMPD must use matched reference parameters

For the main AMPD metric, the two models being compared must receive the **same full reference parameter vector within each Monte Carlo iteration**.

The procedure for one iteration is:

1. Draw one full canonical reference parameter vector.
2. Give that same vector to Model A and Model B.
3. Let each model use the parameters it recognizes and ignore the rest.
4. Evaluate both models over the same payoff structures.
5. Compute the chosen policy-distance metric between the two sets of choice probabilities.
6. Average over payoff structures.
7. Repeat for many parameter draws.

This ensures that AMPD measures the behavioral difference between utility architectures, not accidental differences between two independently sampled artificial agents.

### Why this matters

If parameters are sampled independently for Model A and Model B, then even comparing a model to itself will generally produce a nonzero distance:

```text
AMPD(model_x, model_x) > 0
```

That is wrong for the main model-space metric. It means the function is measuring **within-model variability across independently sampled agents**, not distance between utility forms. Within-model variability can be useful as a separate diagnostic, but it should not be placed in the main AMPD distance matrix.

For the primary AMPD matrix:

```text
AMPD(model_x, model_x) = 0
```

up to numerical precision. In the matrix implementation, the diagonal should be set to exactly `0.0` rather than computed through Monte Carlo sampling.

---

## Canonical full reference parameter vector

Use a full reference vector containing the largest common set of mean parameters used across the utility-function universe. At minimum, this should include:

```text
Vᵢᵢ
Ʌᵢᵢ
Vᵢⱼ
Ʌᵢⱼ
Ƹᵢⱼ
Ʒᵢⱼ
γ1
γ2
γ3
```

Do **not** include the response temperature `τ` / `temp` in this reference vector. AMPD should use the `softmax_temperature` / `choice_temperature` argument as the fixed choice-temperature setting for both models.

Each model then projects the full reference vector onto its active parameter set:

```text
full_reference_params → params_for_model_a
full_reference_params → params_for_model_b
```

Examples:

- A model without altruism ignores `Vᵢⱼ` and `Ʌᵢⱼ`.
- A model with fixed self-interest ignores `Vᵢᵢ`.
- A model with a single exponent uses `γ1` and ignores or collapses `γ2` and `γ3` according to existing utility-function logic.
- A model without social comparison ignores `Ƹᵢⱼ` and `Ʒᵢⱼ`.

The fact that some parameters have somewhat different interpretations in special model families, such as conditional-welfare models, is acceptable. AMPD is a **reference-prior behavioral distance**. It is defined relative to a shared parameter-reference system.

---

## Uniform parameter sampling

For `parameter_sampling_mode="uniform"`:

1. Draw one full canonical reference vector per iteration.
2. Sample each canonical parameter from its bounds.
3. Use `param_bds`, `make_param_info(...)`, and/or `parameter_keys_for_utility_settings(...)` as the authoritative sources for parameter names and bounds.
4. Project the same full vector into both compared models.

Do not call a model-specific sampler separately for Model A and Model B in the primary AMPD path.

---

## Realistic parameter sampling

For `parameter_sampling_mode="realistic"`:

1. Choose one `player_role` from `player_roles` for the iteration, or otherwise use a clearly documented role-combination rule.
2. Draw one empirical row from that role’s population parameter distribution dataframe.
3. Use that row to populate a shared full reference vector.
4. For any canonical parameter missing from the empirical row, sample that parameter uniformly from bounds.
5. Use the same completed full reference vector for both models.

This preserves role-specific empirical realism without allowing Model A and Model B to receive different random agents during the same comparison.

Recommended default:

```python
player_roles: list[Literal["chooser", "predictor"]] | None = ["chooser", "predictor"]
```

The helper should support role-specific AMPD matrices too, especially chooser-only, because utility functions are most directly choice-generating. However, the default can include both roles when using realistic parameter sampling.

---

## Independent parameter draws are a different diagnostic

The implementation may optionally support:

```python
parameter_pairing_mode="independent"
```

But this should not be the default and should not be used for the main AMPD matrix.

Independent draws answer a different question:

> How far apart are two independently sampled agents from these model families?

For `model_x` compared with itself, independent draws estimate within-family policy variability. That is potentially interesting, but it is not a distance between model architectures. Label it clearly, cache it separately, and never use it as the primary AMPD matrix for MDS, clustering, max-min subset selection, or participant-cloud geometry.

# Cross-entropy, entropy, KL, and JSD

## Directional cross-entropy

Cross-entropy is the expected negative log-likelihood of one probabilistic policy when another policy is treated as truth.

If the true/generating policy gives probability `p` to option A and the evaluated policy gives probability `q`, then:

$$
CE(p,q)
=
-\left[p\log(q)+(1-p)\log(1-q)\right]
$$

Use cross-entropy / NLL-style metrics when one side is privileged as truth, such as:

- human data as ground truth;
- a known generating model in a synthetic recovery simulation;
- a fitted model evaluated against held-out data.

---

## Entropy and KL divergence

The Shannon entropy of a Bernoulli policy is:

$$
H(p)
=
-\left[p\log(p)+(1-p)\log(1-p)\right]
$$

The extra directional loss from using `q` when `p` is truth is:

$$
KL(p\Vert q)=CE(p,q)-H(p)
$$

This is useful for directional recovery loss, but it is not symmetric.

---

## Symmetric geometry metric: normalized Jensen-Shannon distance

For model-space geometry, use normalized Jensen-Shannon divergence/distance as the default symmetric AMPD metric.

For a single payoff structure:

$$
d_{JSD}(p,q)
=
\frac{
H\left(\frac{p+q}{2}\right)
-
\frac{1}{2}H(p)
-
\frac{1}{2}H(q)
}{
\log 2
}
$$

Then average across payoff structures and shared parameter draws.

Interpretation:

- `0` = identical policies;
- `1` = maximally different deterministic policies;
- intermediate values = graded behavioral distance.

Normalized JSD is preferred for the main AMPD matrix because it is symmetric, bounded, and directly compares continuous choice probabilities without needing to sample binary responses.

---

## Directional recovery metric: normalized policy regret

When a generating model is known, use normalized policy regret:

$$
R_{policy}
=
\frac{
CE(p^\*,\hat{p}) - H(p^\*)
}{
CE(p^\*,0.5) - H(p^\*)
}
$$

where:

- `p*` = true generating probability;
- `p_hat` = recovered model’s probability;
- `0.5` = random-choice baseline.

Interpretation:

- `0` = recovered policy is as good as the true generating policy;
- `0.05` = recovered model loses only 5% of recoverable predictive information;
- `1` = no better than random;
- `>1` = worse than random.

Use this for recovery simulations and held-out predictive comparisons, not for symmetric model-space geometry.

---

## Simple debug metric: mean absolute probability difference

It may also be useful to support:

$$
d_{abs}(p,q)=|p-q|
$$

Averaged across payoffs and shared parameter draws, this metric is less theoretically elegant than JSD but very intuitive for debugging.

---

## Cache requirements

The AMPD cache must be keyed by all settings that affect the values.

At minimum, include:

```text
metric
parameter_sampling_mode
parameter_pairing_mode
softmax_temperature / choice_temperature
n_games
n_iters
player_roles
random_seed or seed policy
utility-function subset hash

```

The subset hash is important. Do not cache only by `n_models`, because two different 25-model subsets would otherwise collide.

The cache should be retrieved only when all relevant settings match. Otherwise compute a new matrix and write a separate file.

---

## Matrix-level requirements

For the main AMPD matrix:

1. The matrix must be symmetric.
2. The diagonal must be exactly `0.0`.
3. Values must be finite and bounded in `[0,1]` for normalized JSD.
4. Do not compute diagonal cells by Monte Carlo. Set them to zero.
5. Use the same payoff structures for Model A and Model B.
6. Use the same shared full reference parameter vector for Model A and Model B within each iteration.
7. If independent-pairing diagnostics are implemented, write them to a separate cache with `parameter_pairing_mode="independent"` in the filename.

## Implementation cautions

- Do not infer Boolean utility-setting columns by “everything that is not metadata.” Use the canonical setting-column order from `config.py` / `utility_settings`.
- Do not use `bool(row[col])` unless the column is guaranteed to be an actual boolean. `bool("False")` is `True`. Add a robust boolean parser if values may come from CSV strings.
- Do not silently convert exceptions into distance penalties during normal execution. Default to raising. If a penalty mode is useful for exploratory runs, make it explicit with `error_policy="penalty"`.
- Respect the repo’s import flow. If AMPD code lives in a module upstream of `model.py`, pass `utility(...)`, `softmax_(...)`, and/or `build_utility_equation(...)` as callbacks. Otherwise place AMPD downstream where importing those functions is safe.
- Reuse `make_param_info(...)`, `parameter_keys_for_utility_settings(...)`, `utility(...)`, and `softmax_(...)`; do not reimplement utility evaluation.

# Recovery metrics to compute for each simulation run

For each generating model \(m^\*\):

## 1. Exact top-1 recovery
Did the true model rank first?

Good to report, but not enough.

## 2. Top-\(k\) recovery
Was the true model in the top 3 / 5 / 10?

This is much more informative in a full-model search.

## 3. \(\Delta BIC\) of the true model
Compute:

$$
\Delta BIC_{\text{true}}
=
BIC(m^\*) - BIC(m_{\text{winner}})
$$

Useful threshold:

$$
\Delta BIC_{\text{true}} \le 10
$$

means the true model remains in the plausible winning set.

## 4. Rank percentile
Normalize the true model’s rank into \([0,1]\):

$$
\text{Rank Percentile}
=
1-\frac{\text{rank}(m^\*)-1}{M-1}
$$

where \(M\) is the number of candidate models.

## 5. Normalized policy regret
This is the most important “how much did the miss matter?” measure.

## 6. Distance from winner to truth
Use **Average Model Policy Distance** between the recovered winner and the true model.

**Implementation note:** do not recompute AMPD from scratch per simulation run. The precomputed
pairwise AMPD matrix (30-iteration version: `processed/ampd-normalized_jsd-uniform-shared-1p5-625-30-unseeded.csv`;
250-iteration version when available) covers all 480 candidate models. For each recovery run,
look up `AMPD[winner_utility_idx, true_utility_idx]` directly from the cached matrix. This reduces
per-run cost from O(minutes) to O(microseconds) and ensures all simulation runs use a consistent
behavioral-distance reference. The precomputed matrix uses uniform parameter sampling — this is
appropriate as a reference-prior behavioral distance for the recovery question.

## 7. Weighted feature accuracy
Did the recovered winner get the important Boolean settings right?

## 8. Rank-distance correlation
For the full candidate list, correlate:
- distance from each candidate to the true model,
- IC rank or \(\Delta BIC\).

This answers:

> *Does the IC analysis rank models roughly by behavioral closeness to the truth?*

That is much richer than asking only whether the truth came in first.

# Nested-equivalent recovery
## This is essential

Exact syntax recovery is not the right gold standard in a nested model space.

A recovery should count as successful if the winning model is:

### Tier 1 — exact
The same symbolic model.

### Tier 2 — BIC-equivalent
The true model is in the plausible winning set.

### Tier 3 — nested-equivalent
The winner is a child of the true model, and the generating parameters make the parent effectively behave like the child.

### Tier 4 — behaviorally equivalent
The winner is not syntactically identical but has tiny policy regret / policy distance from the truth.

---

## Use existing nesting utilities

# How to score BIC in heterogeneous recovery

If the recovery simulation fits models at the **agent level**, then the complexity penalty should respect that.

A good default is:

$$
BIC_m
=
\sum_i \left(2NLL_{i,m} + k_m \log n_i \right)
$$

where:
- \(i\) indexes agents,
- \(k_m\) is the number of free parameters in model \(m\),
- \(n_i\) is the number of choices from agent \(i\).

This is cleaner than pretending that a single pooled parameter vector generated everyone’s data.

If the codebase already has a standardized BIC pipeline, the coding agent should align with that style as much as possible while respecting the agent-level recovery design.

# Weighted feature accuracy

Because models are defined by **14 Boolean settings**, it is useful to evaluate recovery at the feature level.

## Unweighted version

$$
A_{\text{feature}}
=
1 - \frac{1}{14}\sum_{s=1}^{14}\mathbb{1}(\hat{s}\neq s^\*_s)
$$

## Weighted version

$$
A_{\text{weighted}}
=
1 -
\frac{
\sum_s w_s \cdot \mathbb{1}(\hat{s}\neq s^\*_s)
}{
\sum_s w_s
}
$$

### Candidate weight schemes
1. **Human-data pairwise \(|\Delta BIC|\)** weights  
   Good for empirical stakes, but somewhat circular.
2. **Simulation-derived policy-distance weights**  
   Better for non-circular recovery scoring.
3. **Model-space distance weights**  
   Weight each setting by how much it changes behavior on average.

### Recommendation
Implement all three, then decide later which to report.

# Self-consistency / noise ceiling
## Elegant and useful

This is the best answer to the question:

> *What counts as “good enough” recovery under finite stochastic data?*

### Procedure
For a fixed true model and parameter regime:

1. Generate dataset A.
2. Generate dataset B from the same truth.
3. Run the full recovery pipeline on both.
4. Compare:
   - winner agreement,
   - feature agreement,
   - rank similarity,
   - policy distance between recovered winners.

This yields a **finite-data ceiling**.
If two replicate datasets from the same truth often pick different winners, then exact top-1 recovery should not be expected to be perfect.

This is a beautiful calibration reference.

# How to select subsets of generating models

Do not rely on only one selection strategy.

## A. Targeted benchmark subset
Most interpretable.

Include:
- winner
- parents / children of winner
- top model per \(k\)
- canonical baseline forms
- some rejected-setting models

## B. Max-min Hamming subset
Select models whose 14-setting vectors are as far apart as possible.

Good for symbolic diversity.

## C. Max-min behavioral-distance subset
Select models that are as behaviorally far apart as possible by **Average Model Policy Distance**.

This is often better than Hamming distance because symbolic difference and behavioral difference are not the same.

## D. Random stratified subset
Randomly sample while stratifying by:
- parameter count \(k\)
- major settings
- nested vs sibling families

Use this as a robustness check.

# Model-space geometry analyses
## These are downstream of the distance matrix

Once pairwise model distances are available, a lot becomes possible.

---

## Tier 1 analyses (most likely worth including in the paper)

### 1. Top-model coherence
Take the top \(N\) models by BIC and compute their mean pairwise policy distance.

**Question:** do the top models form one coherent behavioral family, or several distinct ones?

### 2. Distance-to-winner vs \(\Delta BIC\)
For each model:

- \(x = \text{distance to winner}\)
- \(y = \Delta BIC\)

**Question:** do worse-fitting models become worse mostly because they are behaviorally far from the winner?

### 3. Rank-distance correlation in recovery simulations
For each recovery run, correlate:
- candidate distance to truth
- candidate rank / \(\Delta BIC\)

**Question:** does the IC landscape track behavioral truth?

### 4. Feature-level behavioral importance
For each Boolean setting, compute how much flipping that setting changes policy on average.

Then compare that to the paper’s existing pairwise \(\Delta BIC\) analysis.

This produces a very nice 2D interpretation:
- high behavioral distance + high BIC gain = psychologically important and empirically used
- high distance + low BIC gain = psychologically potent but empirically unsupported here
- low distance + high BIC gain = subtle but systematically helpful
- low distance + low BIC gain = likely negligible in this payoff space

---

## Tier 2 analyses (excellent supplement candidates)

### 5. Top-model heatmap
Heatmap of pairwise distances among the top 20 / 50 models.

### 6. Dendrogram / clustering
Hierarchical clustering of utility forms by policy distance.

### 7. Low-dimensional map of model space
MDS / PCA / UMAP-style projection of the distance matrix.

### 8. Sliding-window diversity curve
For models ranked \(r\) through \(r+N-1\), compute mean pairwise distance.

This shows whether the top of the ranking is behaviorally tight or plural.

---

## Tier 3 analyses (probably future work unless very revealing)

### 9. Adjacent-rank cliffs
Distance between rank \(r\) and rank \(r+1\).

### 10. Discriminating payoff structures
Given two model clusters, find the payoff structures where they disagree most.

This is extremely valuable for future experimental design, but probably more of a follow-up / supplement unless it reveals a very clean story.

# Practical note on computational cost

A full `M × M` distance matrix contains:

$$
\frac{M(M-1)}{2}
$$

unique pairs.

This is still much cheaper than repeated optimization, but it is not literally free.

### Suggestions
- precompute the full 625 payoff grid once;
- precompute shared parameter draws;
- cache model-choice probabilities where possible;
- compute pairwise distances in chunks;
- store cached distances by full settings;
- test convergence by increasing `n_iters` and correlating the resulting distance matrices.

The distance layer should be treated as **fast**, but still engineered carefully.

```python
for generating_model in benchmark_generating_models:
    for parameter_regime in parameter_regimes:
        for choice_temperature in temperature_grid:

                            n_games=n_games,

                        )

                            utility_model=generating_model,
                            params=true_params,
                            payoff_structures=payoff_structures,
                            temperature=choice_temperature,
                            general_settings=general_settings,
                        )

                        synthetic_dataset.append(
                            {
                                "true_model": generating_model,
                                "true_params": true_params,
                                "payoffs": payoff_structures,
                                "choices": agent_choices,
                            }
                        )

                    recovery_results = run_existing_ic_pipeline(
                        synthetic_dataset,
                        fit_mode="agent_level",  # recommended main version
                        general_settings=general_settings,
                    )

                    metrics = evaluate_recovery(
                        synthetic_dataset=synthetic_dataset,
                        recovery_results=recovery_results,
                        use_nested_equivalence=True,
                        use_behavioral_equivalence=True,
                        general_settings=general_settings,
                    )

                    save_metrics(metrics)
```

Every batch should log:
- random seeds,
- temperature,

- payoff mode,
- number of iterations,
- benchmark subset definition,
- cache version tag.

Before any large run:
- identical model vs itself
- parent-child anchor equivalence
- distance monotonicity away from anchors
- recovery under clean low-noise conditions

## 5. Treat exact symbolic recovery as only one score
Never present it as the sole standard.
